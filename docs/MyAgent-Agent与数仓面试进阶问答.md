## 第一部分 Agent维度

### A01 Agent与SQL接口或BI工具有什么区别

**直接回答：**SQL接口接受明确查询并返回结果；BI通常围绕预设模型和展示组织分析。Agent还要理解自然语言需求、补齐缺失条件、选择受支持能力、组合工具结果并决定继续、澄清或停止。关键不是有没有聊天框，而是任务控制和证据处理。

**进阶理解：**自主程度是连续的。固定Workflow也可以构成有界Data Agent，但不能因此宣称自由规划。越开放的工具空间，越需要权限、步数、时间和验证边界。数据分析中的错误通常是语义错误，不能只用“SQL能执行”评价成功。

**项目落点与边界：**MyAgent支持指标查询、异常分析及画像读取，UnifiedRuntime分派任务。异常分析会验证用户前提；画像缺日期会澄清。当前主要采用受控Workflow，不能描述成通用自主Agent或完整BI产品。

### A02 一次请求从输入到回答经过哪些步骤

**直接回答：**先识别任务，再解析指标或实体、日期与筛选，读取授权知识和结构化上下文，生成受限任务，校验业务约束，执行Skill与工具，最后返回数值和证据。失败不能绕过校验进入成功回答。

```ascii
Question -> UnifiedRuntime
  |-- metric -> TaskInterpreter -> Task validation
  |             -> Metadata -> LangGraph -> Skill
  |             -> plan -> SQLCompiler -> Worker
  `-- profile -> explicit entity/date -> FeatureRequest
                -> profile-query -> published release -> Worker
Result -> definition + version + quality + evidence
```

**进阶理解：**把理解、规划、执行和展示分开，有助于定位失败。识别错指标和查询引擎超时是不同故障，不能都交给模型反复修SQL。每阶段应有稳定输入输出和明确状态。

**项目落点与边界：**指标走HarnessRuntime及LangGraph；画像走FeatureRuntime。两者共享统一入口和只读Worker思想，但持久化与版本来源分开，画像不依赖原指标快照有效期。

### A03 哪些职责交给模型 哪些必须由代码完成

**直接回答：**模型适合识别业务意图、发现可能的概念、生成结构化任务和提出候选假设；代码负责身份、指标权威、时间边界、合法维度、查询编译、资源控制、对账和发布。不能让模型决定自己拥有何种权限。

**进阶理解：**模型擅长处理语言不确定性，确定性代码适合执行可证明约束。两者的接口应是受限中间表示，而不是任意SQL或任意函数名。候选假设只有通过真实工具验证后才能升级为观察。

**项目落点与边界：**指标模型只输出Task/Query，公式来自commerce.json。画像目前直接用规则识别明确实体和日期，不额外调用模型。最终证据报告由模板组织，不能说全部文字都由模型自由生成。

### A04 澄清 停止 前提反证和证据不足有什么区别

**直接回答：**澄清表示用户补充信息后可能执行；停止表示约束、身份、资源或系统故障阻断执行；前提反证表示数据不支持用户描述的变化；证据不足表示已经得到部分数值观察，但无法确认更强结论。

**进阶理解：**例如“销售额”有歧义应澄清；非法跨事实维度应拒绝或澄清替代口径；用户说下降而查询上涨应反证；金额确实下降但没有独立事件证据，应保留观察且停止因果归因。系统错误不能被包装成业务零值。

**项目落点与边界：**项目使用CLARIFY、STOPPED、PREMISE_REFUTED、INSUFFICIENT_EVIDENCE等状态。画像不存在实体返回found=false；不存在日期版本则澄清。它们不能统一解释为“模型回答失败”。

### A05 自然语言理解需要提取哪些信息

**直接回答：**至少提取任务类型、指标或数据产品、实体、时间窗口、筛选、分组与比较方向。异常问题还需要对照窗口与可下钻维度，不能只抓“转化率”“今天”“下降”三个词。

**进阶理解：**同一句话可能同时涉及口径和时间歧义。“上周销售额为什么低”既可能缺比较基准，也可能不明确销售额是否包含退款或未完成订单。解析应保存用户明确条件与系统推导条件，便于检查是否遗漏或错误默认。

**项目落点与边界：**Task包含query、baseline、expected_direction及diagnosis_dimensions；FeatureRequest包含数据产品、日期和ID。任意OR、多值筛选或画像排名当前不支持，不能静默删掉这些条件继续执行。

### A06 JSON Schema和Pydantic为什么不能证明理解正确

**直接回答：**它们验证结构和类型，例如字段存在、日期可解析、ID为正数或不允许额外SQL字段。它们无法证明“用户说美国”是否已经保留，也无法证明选择的指标符合业务含义。

**进阶理解：**应分三层：结构正确、语义合法、与原问题一致。合法的订单量查询仍可能回答了用户的金额问题；合法日期也可能与问题里的月份不一致。严格结构输出缩小错误空间，却不是模型正确性证明。

**项目落点与边界：**Query拒绝额外字段并限制窗口和维度数量，Task验证同口径比较。还有明确日期/指标与部分筛选遗漏保护；这些一致性检查没有覆盖所有复杂自然语言。模型准确率尚未系统验收。

### A07 销售额和转化率有歧义时怎样处理

**直接回答：**先列出数据能够支持的业务口径并澄清，不按词面自动选公式。销售额可能是下单金额、完成商品金额或净收入；转化率必须明确分子、分母、实体粒度、归属方式与观察窗口。

**进阶理解：**业务同义词不等于指标同义词。“支付成功率”与“订单完成占比”看起来相关，但事实表不同。没有支付尝试数据时，应说明缺失，而不是用完成订单状态占比代替。澄清结果应进入结构化任务并成为证据的一部分。

**项目落点与边界：**合同定义booked_amount为全部状态下单商品金额，明确不是实收。TheLook没有可靠支付事实，不能生成支付CVR或金融核验指标。

### A08 Schema Linking具体链接什么

**直接回答：**它将业务词映射到指标、事实表、字段和字段值。例如“美国男性完成订单占比”对应complete_order_rate、订单事实、国家/性别维度及United States/M。链接不只是找表名。

**进阶理解：**字段存在只是必要条件，还需确认它在当前Grain下可用、适合过滤还是分组、是否敏感、是否有历史版本。存在品类字段的商品表不意味着订单完成占比可以安全按品类拆分。

**项目落点与边界：**KnowledgeRetriever发现候选，注册表给权威定义，DimensionResolver验证实际值，元数据提供来源与质量。这个过程不会凭血缘自动创造合法Join路径。

### A09 如何防止筛选遗漏或未知值造成伪零

**直接回答：**将明确条件与任务中的筛选做一致性检查，并在执行前验证业务值能否唯一链接到真实枚举。未知值先澄清，不能把匹配不到的字符串直接查询成零。

**进阶理解：**“无记录”“明确零值”“未知筛选”“无权查看”是四种不同状态。高基数字段不宜全部塞给模型，可提供有限候选并用精确参数查询验证。多义值必须澄清，不能只选择排名第一的候选。

**项目落点与边界：**美国与男性有规范化映射，枚举采样有上限，高基数值可精确匹配。明确条件保护主要覆盖国家/性别，不能宣称所有筛选遗漏均被识别。

### A10 时间窗口为什么用UTC闭开区间

**直接回答：**闭开区间[start,end)避免相邻窗口边界重复，UTC统一存储与计算避免隐式时区差异。例如9月定义为9月1日零点至10月1日零点之前。

**进阶理解：**统一UTC不意味着业务永远按UTC报表。若支持北京时间业务日，应先将本地边界准确转换成UTC，考虑夏令时和业务日历。窗口还需等长、互不重叠、已结束且不超观测覆盖；“今天”通常不是完整一天。

**项目落点与边界：**当前合同统一UTC，单指标窗口最多31天。未支持的时区语义会澄清或拒绝；快照最大时间不被当成完整性水位。

### A11 多轮追问怎样保留上下文又避免矛盾

**直接回答：**保存上一结构化任务，对新回复做字段级补丁合并，明确哪些字段继承、替换或清空，再重新校验。不要只把所有历史文字拼接成更长Prompt。

**进阶理解：**“改看女性”替换性别而保留日期和指标；“换成商品画像”改变任务类型，原用户ID不能继续混入。日期有冲突时必须澄清。会话还要绑定身份和版本，不能继承另一个主体的上下文。

**项目落点与边界：**画像澄清采用previous字段补丁，缺日期后补日期可继续。指标路径还有原问题与回复文本组合，复杂冲突合并未统一实现。画像完成后的任意省略式追问也不保证支持。

### A12 RAG与微调分别解决什么问题

**直接回答：**RAG在执行时获取外部知识，适合频繁变化的定义、Schema和证据；微调主要改变模型行为或任务表现，不适合替代实时权威目录。正确口径应来自可更新的合同，而不是寄希望于模型记住。

**进阶理解：**检索错内容、模型没遵守约束、工具执行失败是不同问题。应先诊断瓶颈再决定改善检索、Prompt、任务Schema或训练，而不是所有失败都做微调。即使微调后，权限和公式仍需确定性校验。

**项目落点与边界：**项目采用知识检索与结构化上下文，没有进行微调。没有评测证据时不能宣称微调一定比当前方案更好。

### A13 Flat RAG和Structured RAG怎样理解

**直接回答：**Flat RAG通常在平面文档或知识片段中找相关内容；Structured RAG围绕结构化对象、字段、关系和约束组织检索与上下文。项目先用词法候选发现，再根据metric_id解析权威对象。

**进阶理解：**这两个名称并没有要求唯一的工程实现。结构化解析可以使用SQL、图遍历或API，不必使用向量数据库。公式、案例、质量各自有权威等级，不应对它们进行无差别投票。

**项目落点与边界：**RetrievalContext区分semantic、metadata、constraints、dimension_values、components与knowledge_hits。这里“双路”不是词法加向量Hybrid Search，也不是两套检索并行融合。

### A14 词法 向量 混合检索与重排如何选择

**直接回答：**词法擅长精确名称和ID，向量可能改善语义改写召回；混合检索结合不同候选来源，重排对候选精细排序。选择依据是真实失败类型、延迟、成本和可解释性，不能因为流行就全部加入。

**进阶理解：**RRF融合的是排名而不是权威公式；Cross-Encoder通常逐对评分，候选多时开销更大。先按授权范围过滤，再召回和重排，避免未授权信息进入模型。候选指标匹配再好，也要通过权威合同验证。

**项目落点与边界：**目前采用中文片段与英文词法评分、别名加权，没有Embedding、RRF或重排。这些是可选进阶设计，不是已实现能力。

### A15 上下文太多或定义冲突怎么办

**直接回答：**按任务只提供相关指标、粒度、组件、合法维度、有限枚举与质量摘要。优先保留权威定义和执行约束，案例作为辅助；来源冲突不能让模型自己挑一个公式继续执行。

**进阶理解：**应保留版本和来源标识，避免检索到旧定义。上下文压缩不能丢掉单位、分母、时间语义或权限。强类型外壳也不等于嵌套字段都强约束，应逐步定义完整对象Schema。

**项目落点与边界：**结构化定义从授权工具重新读取，异常来源会停止。当前冲突检查主要是来源校验，没有完整多版本业务审批与口径内容冲突治理；多个内层字段仍是dict。

### A16 怎样分别评价检索 理解和执行

**直接回答：**检索看正确候选是否被召回及排序；理解看指标、日期、筛选和澄清是否正确；执行看编译、数据结果、权限和资源边界；最终回答看是否只陈述有证据的结论。这些应分别测量。

**进阶理解：**召回正确不意味着模型选对，SQL结果正确也可能回答错问题。评测集要包含歧义、未知值、非法Grain、无版本、数据不足和错误前提。还要测拒绝是否合理，不能只计算所有请求成功率。

**项目落点与边界：**有工程测试、规则和真实模型烟测记录。当前按用户范围未扩展系统模型准确率评测，不能将14、57或121项工程测试当作自然语言准确率。

### A17 Prompt Engineering与提示注入防护怎样理解

**直接回答：**Prompt应定义任务、可用上下文、输出契约、澄清条件和证据要求，并提供少量边界清晰的例子。它帮助模型行为一致，但不能替代服务端权限、SQL校验和固定工具集合。

**进阶理解：**检索文本可能夹带“忽略规则”类指令，应作为不可信数据处理。不给模型自由SQL或任意工具名，并从可信合同重新读取公式，可降低攻击面。观测记录保存操作与结果摘要，不需要索取或存储模型私有思维链。

**项目落点与边界：**模型输出受限Task，画像只读固定查询，非法输入与部分绕过语句会被拒绝。但未完成系统红队评测，不能宣称提示注入已全面解决。

### A18 Semantic Layer与Metadata职责是什么

**直接回答：**Semantic Layer定义指标怎样算，包括事实、Grain、公式、单位、维度和时间语义；Metadata描述数据是什么、从哪里来、谁负责、是否可信。字段血缘不能自动成为正确的指标定义。

**进阶理解：**公式只维护一个权威来源，目录或知识库可以引用它并提供描述，不再另存独立可修改公式。版本变更应明确影响查询和可比性。业务术语、指标说明和执行公式之间应有映射关系。

**项目落点与边界：**commerce.json是12指标权威，自建目录保存Schema/关系/质量。研究MetricFlow、DataHub、WrenAI的思想，但不调用其核心服务，不把已编译SQL再交给另一个引擎重复编译。

### A19 为什么要有Query中间表示与确定性编译

**直接回答：**中间表示将语言理解与执行分开。模型只选指标、窗口、分组和筛选，编译器从可信定义构造AST与SQL。这样可以独立校验、测试、记录版本并重编译比较。

**进阶理解：**中间表示越强，能表达的业务越受控；代价是必须显式扩展新能力。与自由SQL相比，它牺牲部分探索灵活性换取可证明约束。参数化和AST也分别解决值与结构的安全问题。

**项目落点与边界：**Query禁止额外字段、限制日期和维度；SQLCompiler检查单事实结构。合法SQL仍可能昂贵，所以执行Worker另外限制资源。

```python
# 简化摘录 semantic.py
class Query(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)
    metric_id: str
    start: dt.date
    end: dt.date
    group_by: tuple[str, ...] = ()
    filters: dict[str, str] = Field(default_factory=dict)
```

### A20 比例 distinct与零分母怎样保证正确

**直接回答：**比例先聚合分子和分母，再相除；distinct计数按所需总体重新计算，不随意累加分组结果；零分母返回null而不是0。三者涉及可加性，不能套用统一SUM模板。

**进阶理解：**A组1/10、B组90/100，总体是91/110，不是两组比率平均。用户跨日期出现时，日UV相加会重复计数。零分母表示比率不可定义，返回0会暗示业务表现已知。

**项目落点与边界：**编译器递归展开同事实比例并使用NULLIF，合同限制订单状态占比的状态筛选，购买用户数明确跨组不可加。完整去重状态合并尚未实现。

### A21 合法维度 为什么拒绝隐式Join

**直接回答：**合法维度是与指标事实粒度和定义兼容的维度，不是所有表中出现过的字段。订单可能包含多个品类，如果没有归属或分摊规则，按品类计算订单指标会重复或改变含义。

**进阶理解：**若要支持Join，需定义实体键、基数、路径、时间关联和聚合策略，并检查唯一性。Many-to-many需要桥表或明确权重，不能只靠COUNT DISTINCT补救所有指标。血缘能证明依赖存在，不能证明Join合法。

**项目落点与边界：**当前单事实编译拒绝运行期隐式Join，多事实规划未实现。数仓中可以按设计预聚合生成合适事实，再显式增加新指标合同。

### A22 logical_plan与计划校验有什么作用

**直接回答：**logical_plan记录扫描表、Grain、时间列、窗口、筛选、分组、聚合和组件，让查询可以解释与审计。计划ID与hash将执行绑定到服务生成的内容；执行时重验版本并重新编译比较。

**进阶理解：**hash证明相对可信记录的内容一致，不证明业务定义本身正确，也不是身份认证。编译器逻辑计划不同于数据库物理执行计划；后者解释扫描、连接和算子成本，两者应分开讨论。

**项目落点与边界：**AgentTools.plan/execute负责受控计划。approval_hash不是人工审批。新画像读取没有复用指标plan_id机制，而是固定SQL与hash绑定发布契约，不能描述成所有工具都走同一计划器。

### A23 Agent Loop Workflow ReAct与React怎样区分

**直接回答：**Agent Loop描述任务推进与观察循环；Workflow规定步骤和分支；ReAct强调推理与行动交替，通过外部观察更新后续行动；React是前端技术，和ReAct不同。[ReAct原论文](https://arxiv.org/abs/2210.03629)

**进阶理解：**固定图能在结果后反证并停止，但不等于模型自主选择下一工具。开放ReAct需要约束工具空间、循环次数、证据等级和终止条件。框架、Prompt和自主程度是不同维度。

**项目落点与边界：**项目有聊天循环、LangGraph状态推进和诊断内部有界查询，当前主要是固定Workflow。没有React网页UI，也没有完整自由ReAct。

### A24 LangGraph节点 状态与条件分支是什么

**直接回答：**节点消费当前状态并返回更新，边定义执行顺序，条件边依据状态选择路径。项目状态包含Task、上下文、计划、结果、trace、status与error，分别进入查询或诊断分支。

**进阶理解：**并发节点更新同一字段时需要合并策略，不能假设执行先后；循环要有终止条件和预算。错误处理要确保失败状态不会被后续节点覆盖成成功。状态大小、持久化与敏感信息也要限制。

**项目落点与边界：**build_agent采用有界分支图和guarded节点，STOPPED/CLARIFY转END。当前不是并行自由规划图，持久化由自建Runtime负责。

### A25 如果将来增加动态规划 应该怎样控制

**直接回答：**先定义允许的计划动作、输入输出和前置条件，再让模型在有限集合中选择；每次执行结果反馈后仍校验计划，限制总步数、查询数、时长和可访问范围。

**进阶理解：**计划与执行分离可阻止模型一次提交危险动作。引入新工具前先确定副作用、幂等和授权；失败后不能不断换指标或删过滤以追求成功。动态规划还要比较它相对固定Workflow的实际收益。

**项目落点与边界：**当前没有动态工具循环。可以把这种设计作为进阶回答，但必须说“若扩展会如此设计”，不能写成已实现功能。

### A26 Tool Skill Harness的区别是什么

**直接回答：**Tool完成具体操作，Skill组织可复用领域过程，Harness管理整个执行过程。工具能查询数值，但不知道异常分析应先验证前提再拆解；Skill知道步骤，但不负责所有会话持久化和熔断。

**进阶理解：**三层可以独立测试。工具测契约和返回值，Skill测步骤与证据，Harness测预算、失败和恢复。过度把逻辑放Prompt会难以验证，全部塞进一个大函数又难以复用。

**项目落点与边界：**metric-query、comparison、drilldown、quality-check、anomaly-analysis、evidence-report、profile-query为7项注册能力；独立数据加工Skill另走命令，不计入这7项。

### A27 SKILL文件怎样成为实际能力

**直接回答：**入口文件说明目标、输入、步骤和停止条件，参考文件维护领域口径，注册表声明契约与依赖，执行器校验参数并调用确定性处理器，模板组织最终输出。缺少执行器，文档本身不会执行查询。

**进阶理解：**声明预算不等于预算已强制执行，依赖声明不等于动态DAG引擎。资源hash有助于绑定任务规范，但还需防止文件规则与代码发生偏差。Skill测试应检验业务边界，而不是只检查文件存在。

**项目落点与边界：**SkillExecutor实际读取SKILL和部分references，注册输入Schema，记录事件。总体查询预算由Harness落实，部分Skill预算仍是描述；profile-query声明不自动重试。

### A28 MCP与原生模型Tool Calling是什么关系

**直接回答：**MCP提供工具发现和调用协议；模型Tool Calling是模型输出工具请求的能力。应用可以将MCP工具描述转换成模型可选工具，也可以直接调用本地服务，两者不自动等价。

**进阶理解：**协议统一不代表工具安全。调用方仍需授权、输入校验、限时和结果验证。外部工具描述也不应成为模型自行扩大权限的依据。MCP host、client、server是调用组织层次。[MCP官方架构](https://modelcontextprotocol.io/docs/learn/architecture)

**项目落点与边界：**项目真实运行本地stdio，主Agent进程内调用AgentTools/FeatureTools。指标模型输出受限Task，不是通过原生Tool Calling自由驱动MCP循环。

### A29 本地MCP与远程调用有哪些工程差别

**直接回答：**本地stdio通过进程输入输出通信，适合本机工具边界；远程调用还涉及网络、身份、连接生命周期、超时和服务部署。传输方式不改变工具的业务契约，但改变故障与信任边界。

**进阶理解：**进程内计划存储重启后会丢失，跨进程不能依赖Python对象。工具错误、协议错误和传输错误应分类处理；日志不能污染协议stdout。协议版本与能力要通过实际协商验证，而不是只背某个版本号。

**项目落点与边界：**当前13工具已真实发现与调用，计划ID在指标服务会话内有效。未建设远程MCP、企业认证或高可用平台。

### A30 Harness如何保存状态 恢复与复用回执

**直接回答：**持久化请求、结构化任务、节点状态、查询次数、耗时、事件和回执，绑定主体与版本。恢复时重新授权和规划，满足绑定条件后复用已有只读回执，而不是直接拿旧进程内计划ID。

**进阶理解：**框架checkpointer通常持久化线程图状态，store用于跨线程应用数据；本项目自建存储不能因此称为原生checkpointer。重放遇到写副作用需要独立幂等和事务设计。[LangGraph持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence)

**项目落点与边界：**指标Runtime重放只读图，画像独立存储任务和回执，并在缓存恢复时重验发布产物。它不是任意节点精确续跑，也不能承诺写操作exactly-once。

### A31 超时 取消与执行预算怎样落实

**直接回答：**预算包括总任务时长、单工具时长、调用次数和结果规模。执行前检查剩余预算并预扣真实尝试，执行中尽可能传递取消信号，超时停止Worker，不能只在最终回答中提示“用了太久”。

**进阶理解：**单次HTTP超时与整任务截止不同；多层重试可能放大总时长。取消应传播到子进程，不能只更新UI。元数据和枚举扫描也消耗资源，但未必被事实查询计数覆盖。

**项目落点与边界：**指标默认16次查询/120秒总预算，查询通常30秒上限，诊断自身约60秒。画像Worker15秒，画像会话单次查询预算。所有内层统一deadline及元数据扫描计量尚未完成。

### A32 哪些错误重试 熔断怎样工作

**直接回答：**明确瞬时网络、临时过载或Worker异常退出可有界重试；非法口径、未知值、权限、模型格式错误及账号额度问题通常停止。熔断在连续瞬时失败达到阈值后暂时拒绝调用，冷却后只允许探测。

**进阶理解：**退避和抖动减少集中重试，Retry-After需尊重；不能把永久错误算成“再试会好”。HALF_OPEN应避免同时大量探测。重试不是幂等或恢复的替代品，读与写操作要求不同。

**项目落点与边界：**指标路径最多3次尝试、失败阈值3、冷却30秒，SQLite记录熔断。画像没有自动重试或共享熔断承诺，不能把指标机制概括成所有路径都有。

### A33 权限为什么不能写在Prompt里

**直接回答：**Prompt是行为提示，用户或模型输出不能成为可信身份。服务端必须根据受信主体决定工具、指标、字段和行范围，在查询阶段强制落实，缓存和旧计划执行时也重验。

**进阶理解：**先返回敏感数据再遮盖文字已经越界。聚合小组抑制还可能影响对账，应明确缺失范围。缓存键应包含主体和策略，不能只按SQL共享结果；本地管理员与企业SSO是不同信任模型。

**项目落点与边界：**有本地令牌与聚合主体行范围约束；画像仅允许本地管理主体，受限聚合凭证不能读取用户级画像。没有完整企业ABAC、多租户或同一OS用户文件隔离。

### A34 异常分析为什么先验证前提与可比性

**直接回答：**如果用户描述的下降不存在，后续归因会围绕错误前提编故事。两窗口还必须同指标、同筛选、同单位、同时间语义且等长、不重叠。先比较才知道变化是否真实。

**进阶理解：**即使数字下降，今天未结束、数据未到齐、状态观察年龄不同或口径变化都可能造成不可比。应分开记录数据变化、数学解释和业务假设，并寻找独立反证，而不是只寻找支持下降的维度。

**项目落点与边界：**Task校验可比性，诊断先查询baseline/current，矛盾时PREMISE_REFUTED。缺完整性与历史状态证据时保留INSUFFICIENT_EVIDENCE，不强行给业务根因。

### A35 量价和比例贡献怎样计算 为什么不等于因果

**直接回答：**金额A=n×p可对称分解为量贡献与价贡献；比例R=N/D可对称分解为分子、分母贡献。它们是恒等式解释，不包含实验或独立业务事件，因此不能证明谁造成变化。

```ascii
Amount change:
  volume = (n1-n0) * (p0+p1) / 2
  price  = (p1-p0) * (n0+n1) / 2
Ratio change, when D0 and D1 are nonzero:
  numerator   = (N1-N0) * (1/D0+1/D1) / 2
  denominator = (N0+N1) * (1/D1-1/D0) / 2
Group contribution:
  N_group1/D_total1 - N_group0/D_total0
```

**进阶理解：**分组应覆盖完整互斥集合并对账残差；有截断、抑制或丢组时不能声称完整分解。渠道与国家是替代视角，不能再次相加；小样本与变化幅度也影响解释稳定性。

**项目落点与边界：**真实诊断执行14次查询，占比变化1.6668个百分点，数学拆解对账通过，但causal=false。没有可信历史状态和业务事件，不确认根因。

### A36 可观测性 测试与模型评测怎样分层

**直接回答：**观测记录任务、版本、节点、Skill、工具、耗时、失败和回执；工程测试检查代码约束，数据测试检查来源与加工，模型评测检查理解与工具选择，业务评估检查实际收益。各层证据不能互换。

**进阶理解：**低错误率也可能来自大量错误拒绝，应同时看可处理率与澄清正确性。成本、延迟和安全拒绝是独立指标。日志需脱敏、保留和清理，不能把密钥或原始敏感行长期保存。

**项目落点与边界：**保存14项专项、57项相关回归和较早121项核心记录，存在重叠，不累加。当前不做系统模型准确率；也未建立完整日志TTL与生产观测平台。

## 第二部分 数仓维度

本部分继续回答事实、分层、建模、SQL、特征、时间、质量、血缘和运行工程问题。下文“若生产扩展”均为进阶理解，不表示已完成第三阶段。

### W01 怎样先理解业务事实而不是直接写SQL

**直接回答：**先确认业务过程、实体关系、事件发生条件与一行含义，再定义指标和加工模型。例如浏览、加购、下单、支付、完成和退款是不同事实，时间和归属也不同，不能因为名称相近就互相替代。

**进阶理解：**访谈应问清订单能否拆单、商品行能否重复、支付是否多次尝试、退款是否部分发生、状态是否回写。主键、生命周期和业务时间是建模输入，不是SQL完成后才补的说明。

**项目落点与边界：**TheLook有七张表，orders到order_items是一对多，events通过URI定位商品。没有可靠支付尝试和推荐曝光事实，因此只交付浏览、下单和观察状态，不生成真实CTR或支付CVR。

### W02 ODS和DWD分别负责什么

**直接回答：**ODS/raw保留来源记录与采集证据，便于重算和溯源；DWD把业务明细规范为可用事实，处理类型、主键、去重、时间、关联和质量标记。DWD仍应保留足够业务细节，而不是提前汇总掉。

**进阶理解：**清洗不能默默改变事实。异常行可隔离或保留标记，并明确进入下游的条件。源记录、摄入时间和源版本有助于区分修正、迟到与重复；一次快照不能恢复真实历史摄入过程。

**项目落点与边界：**raw保留原表，DWD有事件、商品浏览、订单商品三表。匿名和未来事件被保留并标记，汇总使用eligible_before_cutoff；原库只读，不被加工脚本覆盖。

### W03 DWS与ADS怎样划分

**直接回答：**DWS按主题和稳定粒度沉淀可复用统计，ADS按具体消费用途组织最终数据。例如用户日行为可以服务画像和报表；用户截止日画像是面向消费方的窗口特征交付。

**进阶理解：**同一个聚合如果被多个应用重复实现，通常应沉淀到DWS。ADS可以是报表、标签或特征宽表，不限于展示。DWS过早写死业务口径会降低复用，ADS无限堆字段又会变成难维护的大表。

**项目落点与边界：**DWS有用户日、商品日、用户商品日和会话；ADS有用户、商品、交互画像。窗口口径通过契约明确，当前一个release保存一个截止日，不向同表无限追加日期。

### W04 为什么不直接做一张大宽表

**直接回答：**不同事实粒度直接拼接会产生重复，明细、汇总和特征还具有不同更新方式。一张表难以同时表达事件、订单、商品和会话的一行含义，质量与血缘也更难验证。

**进阶理解：**宽表适合明确粒度和用途，但不是越宽越好。重复存储和依赖变多会增加更新、权限和回溯成本。分层价值来自复用与明确契约；如果每层只是复制同样字段，确实会产生无意义复杂度。

**项目落点与边界：**先分别聚合行为与交易再关联，ADS只保留交付需要的特征。画像不直接加入姓名、邮箱或未经历史验证的当前属性。

### W05 一张表的交付契约至少包含什么

**直接回答：**名称和用途、主键粒度、字段类型、来源、公式、单位、时间窗口、缺失语义、数据范围、版本、质量和责任人。算法或业务方必须知道怎样使用及哪些操作不成立。

**进阶理解：**例如每天去重浏览用户数不能直接加成月UV，商品订单数跨商品不能加成总体订单数。契约还应说明更新模式、删除规则、SLA和兼容性；字段名相同但窗口变更可能是破坏性变化。

**项目落点与边界：**发布table-contracts.json与metadata.json，说明Grain、列、来源和时间边界。当前没有完整生产SLA与真实Owner治理；原Owner为未验证本地占位责任人。

### W06 Grain究竟是什么 怎样选对

**直接回答：**Grain是“一行代表什么”，必须先于列和聚合确定。订单表一行一订单，订单商品一行一商品明细；用户商品日表一行一个日期用户商品组合，不能混用这些计数口径。

**进阶理解：**主键唯一只能证明存储唯一，不自动证明业务粒度正确。例如错误预聚合后order_id唯一，但金额可能早已被重复。应结合业务定义、来源关系、唯一性和金额数量对账验证。

**项目落点与边界：**订单与订单商品分别建模，日汇总检查复合主键。运行期编译器不为缺维度的订单指标偷偷改成商品事实。面试回答应先说Grain，再说Join和SUM。

### W07 事实表与维度表有哪些区别

**直接回答：**事实表记录业务发生或状态，通常包含业务时间、关联键和度量；维度表描述实体属性，支持筛选、分组和解释。区分依据是业务职责，而不是表大小或有没有字符串。

**进阶理解：**同一个用户可以作为维度，也可产生注册事实；状态变更可能另建事件事实。维度主键要唯一或按时间唯一，关联条件需匹配版本，否则“维表Join”同样可能膨胀。

**项目落点与边界：**dim_users和dim_products描述实体，fct_orders和fct_order_items记录交易事实。特征仓目前避免把无历史版本的维度属性混入过去画像。

### W08 业务主键 代理键和复合键怎么选

**直接回答：**业务主键来自源业务实体，如order_id；代理键是数仓生成的标识，常用于跨源统一或维度版本；复合键表达联合粒度，如日期×用户×商品。选择取决于实体稳定性与历史建模需求。

**进阶理解：**业务ID可能跨系统重复，应附来源命名空间。SCD2用同一业务ID的多个代理版本，事实需要按业务时间匹配版本。不能因为字段名叫ID就默认全局唯一；Null与重复都要检查。

**项目落点与边界：**TheLook本地使用源业务键，DWS/ADS验证复合粒度。没有实现企业跨源主数据和真实历史代理维度，不应声称已解决所有身份统一。

### W09 事务 周期快照和累积快照事实表如何区分

**直接回答：**事务事实记录一次发生，如一笔订单商品；周期快照定期记录状态，如每日余额或库存；累积快照追踪流程里程碑，如下单、发货、送达时间，往往随过程更新。

**进阶理解：**下单金额按发生时间通常可加；库存或余额跨日期求和常无业务意义。累积快照方便分析流程时长，但当前状态回写不能恢复过去当时状态，若需历史应保存事件或版本。

**项目落点与边界：**订单含里程碑字段，但当前原始来源是单次快照，不是完整状态变更流。日画像是按截止日发布的数据产品，不能把它直接等同于完整生产周期快照体系。

### W10 可加 半可加和不可加指标如何判断

**直接回答：**可加指标可以沿合法维度求和，如互斥订单商品金额；半可加只沿部分维度可加，如账户余额可跨账户但不宜跨天；不可加指标如比例、均值、distinct人数需要重新计算或保留组件。

**进阶理解：**可加性依赖业务集合与Grain，不是函数名字。订单数按商品可能重复，日UV跨天不互斥。均值可通过SUM与COUNT合并，比例可通过分子分母合并，distinct则通常需要集合状态或重新去重。

**项目落点与边界：**编译器比例展开组件，用户去重数不随意累加。特征契约说明每日viewer_count不能汇总成月UV，商品订单数不能相加为全局订单数。

### W11 SCD1 SCD2与观察历史有什么区别

**直接回答：**SCD1覆盖属性，只保留当前值；SCD2增加版本行，用有效区间保留历史变化。观察历史记录“何时看到某版本”，不必等于业务真实生效时间。两种时间不能混为一谈。

**进阶理解：**历史Join要满足valid_from≤事实时间<valid_to，并保证同实体区间不重叠。若记录迟到，业务生效时间与系统获知时间不同，严格历史可用性可能需要双时间设计。

**项目落点与边界：**已有SnapshotHistory记录观察版本，但不是业务有效时间SCD2。画像没有将当前地区、年龄等直接作为过去特征，也不宣称商品历史可售性已验证。

### W12 Join Fanout怎样发生与解决

**直接回答：**一对多关联会把左侧记录复制，多条一对多分支还会相乘。例如订单金额100关联三条商品，SUM订单金额得到300。应先将各分支聚合到目标Grain，再关联唯一键并对账。

**进阶理解：**COUNT DISTINCT只能修复特定计数，不能修复所有金额。SUM DISTINCT(amount)会把不同订单同金额误去重。正确策略来自业务关系与可加性，而不是随意换聚合函数。

```sql
-- 教学示例：先聚合，再保持每订单一行
with item_totals as (
  select order_id, sum(booked_item_amount) as amount
  from commerce.fct_order_items
  group by order_id
)
select o.order_id, i.amount
from raw.orders o
left join item_totals i on o.order_id = i.order_id;
```

**项目落点与边界：**fct_orders按此思想建模；行为和交易DWS也分别预聚合。主键和raw金额对账共同验证，没有依赖模型推断关联正确性。

### W13 LEFT JOIN WHERE与ON为什么会改变结果

**直接回答：**ON控制哪些右表记录匹配，WHERE控制关联后的哪些行保留。LEFT JOIN后在WHERE要求右表字段满足条件，常会排除未匹配Null行，使结果在该条件下表现为内关联。

**进阶理解：**要保留无行为商品并补零，通常先过滤右侧子查询或把条件放ON；但不能机械移动所有条件，因为业务含义可能变化。事实范围与维度匹配条件应分开设计，并用无匹配样例验证。

**项目落点与边界：**ADS从实体或交互keys左关联统计，缺统计补合法零值。缺实体记录仍返回found=false，不把“无实体”和“存在实体但零行为”合并。

### W14 COUNT DISTINCT Null与空结果怎么理解

**直接回答：**COUNT(*)计行数，COUNT(col)计非Null值，COUNT DISTINCT计不同非Null值。SUM等聚合通常忽略Null，但空组SUM为Null而不是0；结果缺失、未知和明确零值要按业务区分。[DuckDB聚合文档](https://duckdb.org/docs/lts/sql/functions/aggregates)

**进阶理解：**COALESCE不能到处使用。无匹配统计时补0可能合理，未知价格或未知付款不能补0后当真实金额。多个Null参与关联与比较时有三值逻辑，判断应使用IS NULL等明确条件。

**项目落点与边界：**画像存在实体但窗口无行为可补0；不存在实体返回空记录。金额对账使用Decimal，比例零分母保留null。独立总量检查对空窗口总和按0解释，范围仅限这些总量断言。

### W15 窗口函数与GROUP BY怎么选择

**直接回答：**GROUP BY压缩为每组一行；窗口函数保留原行，同时计算组内排名、累计或前后关系。去重可用ROW_NUMBER，时序比较可用LAG，连续累计要明确窗口框架。[DuckDB窗口函数文档](https://duckdb.org/docs/lts/sql/functions/window_functions)

**进阶理解：**ORDER BY相同值的排序可能不确定，需要稳定并列规则。RANGE与ROWS框架在同时间多条记录时不同；全表排序可能消耗大量内存。技术去重还需知道是重复消息还是更正版本。

**项目落点与边界：**DWD事件使用ROW_NUMBER选择记录，但原始重复会触发行数/唯一性验收失败，不声称已实现完整版本修正策略。会话按session_id聚合，不使用窗口切断现有会话。

### W16 多对多关联应该怎样建模

**直接回答：**先明确实体关系是否真的多对多，以及指标需要重复归属、主归属还是权重分摊。可用桥表表示关系，权重分摊必须保证合理归一和有效时间；不同解释会产生不同指标。

**进阶理解：**一张订单包含多个品类，按品类统计订单数可能允许多归属，但就不能跨品类加成总订单数；若按金额分摊，分母和权重需明确。不能凭一个技术Join替业务选择归属规则。

**项目落点与边界：**用户商品交互的粒度显式为用户×商品×日期，关联的是同粒度汇总。订单指标运行期不支持未定义的多对多品类拆解。

### W17 事件数据清洗应该检查什么

**直接回答：**主键、重复、时间、类型、实体引用、URI解析、身份缺失和字段范围。必须区分保留原事实、标记异常和下游可用性，避免清洗时把数据悄悄变成另一种业务事件。

**进阶理解：**异常率、未知事件类型和空时间都是质量指标。隔离记录需可追溯并能解释数量差；去重规则应明确优先级和稳定排序。浏览事件不能因业务希望计算CTR就改称点击。

**项目落点与边界：**DWD保存is_anonymous、unknown_user、future_at_capture、invalid_product_reference和eligible_before_cutoff。数据源存在1,672条晚于采集时点事件，已标记并排除相关汇总，不修改原始时间。

### W18 匿名与登录用户怎样处理

**直接回答：**匿名事件可以按会话或商品统计，但没有可靠身份关系就不能回填用户。一个session出现多个用户时要标记混合身份，不能随意选一个用户覆盖全部行为。

**进阶理解：**身份拼接涉及登录切换、跨设备、共享设备和有效时间，需要来源证据与合规策略。算法需要用户历史时，可选择仅登录行为或单独匿名session模型，而不是把session_id当user_id。

**项目落点与边界：**保留1,124,193条匿名事件，商品主题包含匿名浏览，用户主题仅可识别用户。会话统计observed_user_count和mixed_user_identity，只有观察到一个用户时给出observed_user_id。

### W19 会话为什么不能按天简单切开

**直接回答：**会话可以跨午夜，按日期拆开会重复计算session并破坏首末时间、事件数和转化观察。已有可靠session_id时优先按它组织完整观察范围，再明确按首事件日等规则归属分析日期。

**进阶理解：**没有session_id时可按用户与间隔阈值划分，但阈值是业务定义，不能替代真实结束事件。即使最后一次观察发生在窗口内，也不能证明会话已结束；水位与结束信号不足时应标记截断或未知。

**项目落点与边界：**dws_session_behavior按session_id跨日聚合，窗口外事件不进入观察。session_closure_verified固定false，时长为观察时长，不是认证的完整会话时长。

### W20 CTR CVR与purchase标签的事实条件是什么

**直接回答：**CTR需要曝光与关联点击；CVR需要明确触发实体、转化事实、归属规则及观察窗口。purchase事件只能证明观察到该事件，不能自动证明订单关联和支付成功；未观察到也不自动成为负例。

**进阶理解：**重复曝光、重复点击、跨设备和延迟转化会影响分母与归因。标签成熟期内的未转化通常不能直接当负样本。离线数据工程应提供label_status、截止和覆盖，而不是只有0/1。

**项目落点与边界：**没有真实曝光/点击链路和支付事实。会话使用OBSERVED_PURCHASE_EVENT或UNKNOWN_NOT_VERIFIED_NEGATIVE，order_attribution_verified和payment_success_verified均false。

### W21 面向推荐的数据开发需要交付什么

**直接回答：**交付可用明细、用户/商品/交互统计与特征契约，让算法方知道每个值的来源、截止时点、窗口和缺失语义。职责是稳定生产正确数据，不要求先训练排序或召回模型。

**进阶理解：**算法方还可能要求候选实体全集、训练样本键、标签和online/offline一致性。数据方必须澄清事实是否存在，以及候选集合是否在预测时点已知。点击预测与购买推荐不是同一数据产品。

**项目落点与边界：**已交付用户、商品、用户商品画像和会话主题。没有推荐算法、线上特征服务或完整训练样本体系；用户商品缺记录不是显式负例。

### W22 特征类型与默认值如何设计

**直接回答：**统计特征要定义窗口、计数对象和单位；类别特征定义字典与未知值；时间特征定义时区和起点。默认值应表达业务语义：无发生可为0，未知或无法计算应为Null或显式状态。

**进阶理解：**数值范围、精度、稳定性和可重复性应入契约。金额用Decimal避免原始浮点误差传播；极大金额贡献计算转float后仍需容差。缺价格不是免费，新用户不是缺数据，缺实体不应补零。

**项目落点与边界：**ADS包含7/30天浏览、30天下单量与Decimal金额、最近交互间隔。Null最近下单时间意味着无已观察订单。当前类别历史特征未加入，避免未经验证的过去属性。

### W23 历史窗口与预测截止点怎样定义

**直接回答：**特征只用截止点前允许的历史数据。UTC 9月8日零点的7天特征使用[9月1日,9月8日)，不是从9月8日向后看。先确定样本粒度和截止，再定义窗口。

**进阶理解：**日特征可基于日汇总合并，但最近一次交互等需要保留时间。统计窗口外的历史记录可能影响“距上次购买”而不影响30天次数，两个口径应分开。业务本地日要先准确转换边界。

**项目落点与边界：**特征as_of固定UTC排他日期，7/30天分别按DWS过滤，最近下单从更长已观察历史取最大时间。不能把所有近期特征都限制在30天而误称全历史间隔。

### W24 event_time ingested_at与watermark怎么区分

**直接回答：**event_time表示业务发生，ingested_at表示系统收到，as_of表示特征截止，observed_at表示快照观察，watermark或完成收据表达某范围数据已按契约到齐。最大事件时间不能代替完成证明。

**进阶理解：**迟到事件可能业务时间早但摄入晚；把它用于过去线上决策特征可能泄漏当时未知信息。即使截止日期早于快照采集，也不能证明当时所有数据均可用。缺业务水位应明确未知。

**项目落点与边界：**本地DWD的ingested_at使用统一源快照观察时间，没有真实逐条历史摄入记录。已实施事件时间排除，但不能宣称严格生产point-in-time认证。

### W25 数据泄漏与point-in-time一致性怎样解释

**直接回答：**泄漏是使用预测时点不应可知的信息，例如未来购买、最终订单状态、全量拟合的统计或未来更新属性。PIT一致性要求特征符合该时点可用数据和版本，而不只满足event_time早于截止。

**进阶理解：**离线重放要区分业务生效和系统获知；训练预处理需只在训练范围拟合，再应用验证集。当前商品目录不能证明商品在过去已经可售。即使不训练模型，数据方也要保障交付口径不会泄漏。

**项目落点与边界：**未把最终状态作为历史特征，当前用户属性也不直接写入过去画像。但缺真实摄入和属性历史，所以仅能说事件时间窗口已约束，历史可用性未验证。

### W26 冷启动 缺失和零行为怎么处理

**直接回答：**实体存在且窗口内无行为可以交付零统计；从未有交互的实体是冷启动；实体未出现在该版本中是不存在记录；字段来源不明是未知。四者应分别表示。

**进阶理解：**推荐方可用商品内容或业务默认策略应对冷启动，但数据方不能把缺记录补成负标签。用户历史长度、字段覆盖或cold_start标记有助于消费方判断置信程度。

**项目落点与边界：**用户/商品画像保留实体全集并补合法统计零，交互画像只覆盖历史已有对。工具查询无实体时found=false，不伪造整行零特征；完整冷启动策略尚未实现。

### W27 用户商品笛卡尔积与候选补特征怎样处理

**直接回答：**10万用户乘2.9万商品约29亿组合，绝大多数没有交互，直接生成会浪费存储且制造不可靠负例。优先产已有交互对，或接收算法方候选键后按需补特征。

**进阶理解：**候选表必须定义request_id、候选生成时点、用户商品键和重复规则。补特征要按同一个截止版本关联，找不到时区分冷启动与版本缺失。候选来源和采样分布也影响训练解释。

**项目落点与边界：**当前交付181,909条已有交互画像，没有全量笛卡尔积；算法方候选批量补特征是可扩展设计，当前工具仅支持单用户商品对读取。

### W28 数据质量应该分几层 独立对账为何重要

**直接回答：**字段层检查空值和范围，实体层检查主键，关联层检查引用，业务层检查金额数量与状态，加工层检查明细到汇总，交付层检查窗口、版本和粒度。独立对账避免同一错误同时存在于模型和镜像测试。

**进阶理解：**只测“表有数据”无法发现Fanout或错窗口。应从raw用不同路径重算核心真值，并覆盖全部实体而不是只查一个样本。对账还要明确过滤范围与匿名排除，不能比较不同总体。

**项目落点与边界：**23项dbt检查与48项独立对账通过，包含所有画像/交互特征及会话首末时间和purchase数。当前测试不证明源端没有漏数，也不代表模型准确率。

### W29 dbt tests与独立验收各自证明什么

**直接回答：**dbt数据测试检查模型数据是否违反断言，例如唯一、非空、关系和自定义失败行；独立验收从来源重新核对交付结果。它们互补，不应把旧PASS拿来证明已变化的新数据。[dbt数据测试](https://docs.getdbt.com/docs/build/data-tests)

**进阶理解：**测试也依赖契约是否完整。常见失误是使用相同错误SQL生成expected，或忽视无数据、边界时间和重复引用。模型单元测试与真实数据断言分别针对逻辑和当前质量。

**项目落点与边界：**发布会重跑物理库断言与独立金额对账；特征构建额外从raw验证画像。源码/数据变更后需重新验证，而不是改时间戳伪造新鲜度。

### W30 发布快照与active指针如何保证交付稳定

**直接回答：**先在候选目录构建和验收，生成数据、契约、血缘与质量文件，通过后再切换成功版本指针。消费方选择一个release，在同一版本中读取，失败不能覆盖上一成功版本。

**进阶理解：**单文件指针替换不等于所有跨资源操作原子。生产还需要处理并发发布、失败清理、消费者缓存、保留与回滚。hash能发现变动，但在同一OS用户可改全部文件的环境下不是完整安全边界。

**项目落点与边界：**特征仓每release独立库及元数据文件，绑定hash后切换active。原指标目录仍有共享可变SQLite的发布一致性风险；两套发布实现不能统一称为分布式原子事务。

### W31 表级 值血缘与控制血缘怎样区分

**直接回答：**表级说明依赖哪些表；值血缘说明输出值由哪些字段计算；控制血缘说明哪些关联、筛选和分组影响进入计算的记录。COUNT(*)还涉及行集合依赖，不能强行说来自一个金额字段。

**进阶理解：**技术解析会遇到星号、CTE、别名、相关子查询、UDF和动态SQL。应给解析范围、未解析字段与截断，而不是输出一张图就宣称完整。影响分析也应区分可达依赖和业务指标实际变化。

**项目落点与边界：**SQLGlot结合真实schema解析字段，控制依赖单列。原目录SQLite，新数据产品JSON交付；尚未统一为完整企业知识图谱。没有专用图数据库依赖。

### W32 全量与增量有什么区别

**直接回答：**全量从指定来源范围重新构建，便于验证但开销高；增量只处理新建或变更范围，必须定义输入识别、唯一键、更新和删除语义。追加只是增量的一种，不能处理全部更正问题。

**进阶理解：**增量模型需要确保增量SQL与全量语义一致，unique_key不是业务正确性证明。历史属性或迟到改变时，受影响范围可能超出最新分区。[dbt增量文档](https://docs.getdbt.com/docs/build/incremental-models)

**项目落点与边界：**当前dbt采用table全量重建，已验证重复结果稳定。生产增量MERGE、迟到修正、补数按用户要求未实施；这题只作概念储备。

### W33 幂等 补数和重复稳定性有什么区别

**直接回答：**幂等关注同一操作重复不造成额外影响；补数重建或修正缺失历史范围；重复稳定性验证相同输入得到相同内容。当前全量替换的稳定性不能自动证明增量消息幂等。

**进阶理解：**如果生产扩展，需要批次ID、输入hash、业务版本与确定性更新规则；同ID同内容可复用，同ID不同内容需冲突处理。不能用简单行数相等证明字段没变，也不能将交换性内容摘要当密码学证明。

**项目落点与边界：**同截止日重建两次，对10表行数和两种行内容摘要比较，再独立对账。没有生产批次登记和补数调度，不宣称已完成第三阶段。

### W34 迟到 更正 删除怎样影响汇总

**直接回答：**迟到增加过去事件，更正可能改变原日期、用户或商品，删除需要可信删除标记。应找出旧、新影响范围并重算，不仅把最新值累加到当前日期。

**进阶理解：**一个9月5日事件会影响包含它的已发布7/30天画像；若从A商品改为B商品，两边都要修正。来源批次没出现记录不等于删除。在线可用历史与事后业务真值还应分开。

**项目落点与边界：**没有实施上述生产链路；现有快照与观察历史不能冒充真实迟到事实。面试只能解释设计思路，不能列为已落地成果。

### W35 分区 执行计划与查询性能怎样分析

**直接回答：**先看扫描范围、列数、过滤位置、Join基数、聚合和排序，使用引擎实际执行计划与耗时定位瓶颈。分区只在查询能裁剪且布局合适时有效，不是任何SQL加日期条件都自动快。

**进阶理解：**小文件、过细分区、重复全文件hash和高基数聚合都可能成为瓶颈。逻辑粒度与物理布局是两件事；本地列式执行与分布式引擎的优化策略也不能直接套用。

**项目落点与边界：**使用DuckDB本地表，没有实现生产分区。Worker限制资源；每次release校验全文件hash有可测I/O成本，元数据扫描与重复计划也仍需优化。

### W36 数据倾斜 广播 Shuffle与故障恢复怎么理解

**直接回答：**分布式Shuffle按键重分配数据，热点键会造成倾斜；小维表广播可减少某些重分配，但内存不足会失败。恢复要求调度知道依赖、已完成范围和失败边界，不能盲目重复整个链路。

**进阶理解：**可考虑预聚合、热点分离或加盐，但加盐后必须按业务重新合并，distinct与Join规则尤其谨慎。广播阈值、执行算子和恢复机制依赖引擎与版本，应依据计划验证。

**项目落点与边界：**项目实际使用DuckDB/dbt，不是Spark/Flink生产系统。本地构建保存日志、失败不切active；没有分布式调度、倾斜实战或增量故障恢复。不可把概念理解写成真实使用经验。

## SQL与代码练习答案

以下为教学示例，不是新的执行验收记录。命名优先使用本项目表；生产方言和窗口需要按实际契约适配。

### 练习一 求总体完成占比而不是平均分组占比

```sql
select
  cast(count(*) filter(where order_status='Complete') as double)
    / nullif(count(*),0) as complete_rate
from commerce.fct_orders
where order_date >= date '2026-09-01'
  and order_date < date '2026-10-01';
```

答案解释：先按同一个事实范围形成分子分母，再除。不能先WHERE order_status=Complete，不能把各渠道rate做AVG。若需要分组，增加合法维度GROUP BY，但总体仍重新聚合组件。

### 练习二 求七天浏览与保留无行为用户

```sql
with recent as (
  select user_id,sum(product_view_count) as views_7d
  from dws.dws_user_behavior_day
  where activity_date >= date '2026-10-04'
    and activity_date < date '2026-10-11'
  group by user_id
)
select u.id as user_id,coalesce(r.views_7d,0) as views_7d
from raw.users u left join recent r on u.id=r.user_id
where u.created_at < timestamptz '2026-10-11 00:00:00+00';
```

答案解释：窗口先过滤在统计分支，左关联保留截止前存在用户。零表示存在用户但无窗口行为；如果读取整个实体结果都不存在，应返回found=false，而不是新造一行。

### 练习三 按月去重用户而不是相加每日UV

```sql
select count(distinct user_id) as logged_in_viewers
from dwd.dwd_product_view
where eligible_before_cutoff
  and event_time_utc >= timestamptz '2026-09-01 00:00:00+00'
  and event_time_utc < timestamptz '2026-10-01 00:00:00+00';
```

答案解释：从明细按总体集合去重。匿名user_id为Null，不纳入登录用户UV；匿名浏览仍可单独统计。不要把匿名会话数命名为总用户数。

### 练习四 复合粒度与孤儿引用检查

```sql
select activity_date,user_id,product_id,count(*) n
from dws.dws_user_product_day
group by activity_date,user_id,product_id
having count(*)>1;

select i.id
from raw.order_items i left join raw.orders o
  on i.order_id=o.order_id
where o.order_id is null;
```

答案解释：第一条找同粒度重复，第二条找孤儿订单引用。没有返回失败行才通过相应断言，但不能因此证明金额或完整性正确。

### 练习五 分支预聚合后关联用户商品

```sql
with v as (
  select event_date d,user_id,product_id,count(*) views
  from dwd.dwd_product_view
  where eligible_before_cutoff and user_id is not null
  group by 1,2,3
), o as (
  select order_date d,user_id,product_id,count(*) items
  from dwd.dwd_order_item
  where eligible_before_cutoff and not missing_order
  group by 1,2,3
)
select coalesce(v.d,o.d) d,
       coalesce(v.user_id,o.user_id) user_id,
       coalesce(v.product_id,o.product_id) product_id,
       coalesce(v.views,0) views,coalesce(o.items,0) items
from v full outer join o using(d,user_id,product_id);
```

答案解释：分别形成同一目标Grain再关联，保留只浏览或只下单的组合。示例省略部分质量标记，真实模型还过滤未知用户、商品、身份不一致和非法金额。

## 实战场景完整回答

### 场景一 今天转化率比昨天低

先问转化率是会话purchase、订单完成占比还是支付成功率；检查数据是否支撑。再确定时区和今天是否结束。若今天未结束或没有覆盖证明，不把全天昨天与部分今天直接相比。口径明确且窗口可比才查两值，反证变化方向，再拆组件和维度。没有业务事件和状态历史时只报告观察，不能确认根因。

项目答案：支付事实不存在需要澄清；当前订单完成占比是快照状态口径，不冒充支付率。完整性水位未知，即使数学拆解通过，仍可能INSUFFICIENT_EVIDENCE。

### 场景二 推荐方要一张用户商品特征表

先明确截止时点、目标键、候选范围、7/30天窗口、浏览与购买定义、默认值和标签责任。分别聚合浏览与订单商品，再按用户商品日期关联；生产画像只覆盖已有对或明确候选，不做全量笛卡尔积。检查复合唯一、总量金额、时间泄漏、来源与交付版本。

项目答案：已落181,909条交互画像，没做算法模型或采样负例。缺交互不表示不喜欢，当前商品全集历史可售性仍未知。

### 场景三 同一个问题恢复后数值变了

先检查身份、策略、指标与数据release、知识/Skill资源是否一致，再区分原查询结果和新执行。不同版本应明确说明而不是拼接旧回执；相同绑定下检查原回执、重编译计划和数据产物hash。重复执行不应改变readonly结果，但现实数据源或公式变化可能使比较不成立。

项目答案：指标路径版本绑定，画像恢复重新校验原发布hash。知识、Prompt和模型配置的完整版本绑定仍不充分，是可改进点。

### 场景四 dbt检查通过但业务说金额不对

先问金额到底是下单还是实收、是否包含取消/退款，再查来源范围、Grain、时间、Join和过滤。将raw、DWD、DWS、ADS分层对账，定位首次差异，而不是先改Prompt。测试只覆盖已写断言，口径缺陷或漏数不一定触发。

项目答案：有raw商品价格到订单商品/订单金额独立对账，能发现关联或加工变化；不能证明支付实收和源完整性，因为没有相应事实。

### 场景五 会话没有purchase 可以标0吗

必须先有明确标签触发、成熟观察窗口、结束或覆盖条件，再确定负例。仅当前快照没出现purchase，可能是未结束、延迟、匿名或事件未到齐。标UNKNOWN，并区分观察到购买与支付成功。

项目答案：UNKNOWN_NOT_VERIFIED_NEGATIVE；session_closure_verified、order_attribution_verified、payment_success_verified均false，避免伪负标签。
